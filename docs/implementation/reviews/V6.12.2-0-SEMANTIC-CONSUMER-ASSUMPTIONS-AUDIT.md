## Lifecycle assumptions (v0.1 bridge)

Confirmed in `packages/core/src/persisted/from-trace-event.ts`:

1. `step_started` → kind from step type (`TOOL`/`LLM`/…), `status: "running"`, `attributes.stepId`, optional `parentId` (often parent **stepId**, not eventId).
2. `step_completed` → **always** `kind: "LOGIC"`, `name: stepId`, terminal status, **no parentId**, `attributes.stepId`.
3. `run_started` / `run_completed` → both `RUN`; start remains `running` if not paired.

Therefore any consumer that treats “finished TOOL” as `kind===TOOL && status!==running` misses bridged completions, and any consumer that treats every `running` row as incomplete fails completed pilots (N-1 / N-3).

## Parent / forest assumptions

- Orphan rule: `parentId` must exist in the **same** event-id map.
- v0.1 parents are frequently **stepIds**; without normalization they look like orphans (N-1 forest).
- Absorbed completion eventIds must not remain as parent targets after pairing.

## Token safety assumptions

- `isSafeRawContentMetricPath` requires leaf ∈ usage count keys and **immediate parent** ∈ safe prefixes.
- Path `attributes.metadata.tokens.input` has parent `tokens`, not `tokenUsage` → flagged UNSAFE (N-2) until `tokens` is accepted.
